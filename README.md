# planner-backend

The backend for **Planner**, an iOS-first day planner (the app lives in `planner-app`, Expo).

The app reads and writes only its local SQLite database. PowerSync streams each user's rows down
from Postgres, and sends the app's queued local writes up to this API, which checks them and writes
Postgres. Later this API also hosts MCP (`/mcp`), the Siri routes and the Google Calendar worker.

```
 Postgres (Supabase) ── logical replication ──▶ PowerSync Cloud ──▶ app (SQLite)
        ▲                                                             │
        └──────── planner-backend (Hono, Cloud Run) ◀── POST /sync/upload ┘
```

The full plan: `planner-app/notes/backend-plan.md`.

## Running locally

Needs Node 22+, pnpm, and Docker running.

```bash
pnpm install
pnpm db:start                  # local Supabase (Postgres + Auth) in Docker, migrations applied
pnpm dev                       # API on http://localhost:8787 (reads .env if present)
pnpm typecheck && pnpm lint && pnpm test
```

The defaults in `src/env.ts` point at the local Supabase, so no `.env` is needed locally. Tokens
are checked against the Supabase JWKS (local Supabase signs with ES256, like cloud projects).

The tests run against the local Supabase: they create real users through the Auth admin API and
sign in for genuine access tokens. `pnpm db:start` must be running.

Model changes: edit `src/db/schema/`, then `pnpm db:generate` (a new migration in
`supabase/migrations`) and `pnpm db:reset` (re-applies everything; wipes local data).

## Layout

```
src/
  db/schema/        the data models (Drizzle), one file per table, with RLS policies
  db/client.ts      Drizzle client (postgres-js pool)
  db/as-user.ts     run queries as the signed-in user (role `authenticated`, RLS applies)
  auth.ts           Supabase access-token check (JWKS, or the legacy HS256 secret)
  routes/sync.ts    POST /sync/upload
  app.ts            the Hono app (GET /health, /sync)
  server.ts         Node server entry
test/               Vitest, against the local Supabase
supabase/           local Supabase config and migrations (generated by drizzle-kit)
powersync/          sync config (Sync Streams, edition 3): each user gets their own rows
infra/              Pulumi: Cloud Run, Artifact Registry, Secret Manager (see infra/README.md)
Dockerfile          the API image (Cloud Run)
```

## API

- `GET /health`: `{ ok: true }` when the database answers.
- `POST /sync/upload` (`Authorization: Bearer <Supabase access token>`): body
  `{ batch: [{ op: 'PUT' | 'PATCH' | 'DELETE', type: '<table>', id, data? }] }`, the changes
  PowerSync queued on the device. Response `{ applied, rejected: [{ index, type, id, reason }] }`.

Upload rules:

- Only `tasks` and `habit_days` can be written (`external_events` is server-only). Columns are
  allowlisted and validated from the models (types, enums, required columns).
- `user_id` is always the signed-in user. A change naming anyone else is rejected.
- References (`tasks.list_id`, `habit_days.habit_id`) must point at the user's own tasks.
- The whole batch is one transaction, run as the user, so Row Level Security applies too.
- A change that can never succeed (invalid data, someone else's row) is **acknowledged and logged,
  not retried**: an error would make the app resend the batch forever and block its queue. Each
  change has its own savepoint, so a rejected one doesn't undo the rest.
- Failures that might pass later (database unreachable) return **503**, and the app retries.
- Conflicts: last write wins per field.

## Decisions

- **Hono on Node** (`@hono/node-server`), bundled with tsup, in a multi-stage Docker image on Cloud
  Run (port 8080, non-root, graceful shutdown on SIGTERM).
- **This repo owns the data models.** The app keeps a hand-synced copy; later both move to a shared
  `planner-utils` package. Schema changes are two-step (add, then remove once old apps are gone).
- **RLS on every table** (`user_id = auth.uid()`), declared next to the tables. The API also runs
  each batch as the user (`set local role authenticated` + `request.jwt.claims`), so RLS is a
  second line of defence behind its own checks.
- **Token checks**: Supabase's JWKS (asymmetric signing keys) by default. The HS256 shared secret is
  accepted only when `SUPABASE_JWT_SECRET` is set (older projects).
- **Tests hit a real local Supabase** (real users, real tokens, real RLS) rather than mocks.
- **Pulumi (TypeScript)** for GCP, one stack per environment. Secret values are added with
  `gcloud`, never stored in Pulumi.
- **CI** (GitHub Actions): typecheck, lint, format check, infra typecheck, tests against
  `supabase start`, and a Docker build. Deploys come later, once the cloud projects exist.

## Blocked on Samuel

These need accounts, consoles or secrets:

- Supabase cloud projects, **dev** and **prod** (then `supabase db push --remote` the migrations, and create
  the PowerSync replication role there).
- A **PowerSync Cloud** instance per environment: connect it to Supabase, point it at the Supabase
  JWKS, and deploy `powersync/sync-rules.yaml`.
- **Sign in with Apple** (Services ID + key) and a **Google OAuth** client, configured in Supabase
  Auth.
- A **GCP project** for deploys (then `infra/`: `pulumi up`, secrets, Workload Identity Federation
  for GitHub Actions deploys).
- Connecting the app: the PowerSync connector in `planner-app` (`uploadData` → `/sync/upload`).
